# REEFS_ML — Codebase Architecture

> Physics-Informed ConvLSTM for Great Barrier Reef Coral Bleaching Prediction

```bash
git clone https://github.com/[repo]/REEFS_ML
```

## Data Flow

```
NOAA ERDDAP OPeNDAP
    ↓ (Strategy 1: .nc URL subset)
    ↓ (Strategy 2: pydap DAP4 stream)
    ↓ (Strategy 3: synthetic fallback for CI/offline)
DataIngestionFSM
    → Variable-specific temporal aggregation, bilinear interpolation to inclusive 0.05° canvas
    → Z-score normalize SST (training split stats only)
    → Write to unified_gbr_canvas.zarr (chunks: time=30, lat=-1, lon=-1)
    ↓
ReefDataset (PyTorch)
    → Sliding window: x=(t-lookback:t), y=(t:t+horizon)
    → Chronological split (no shuffling across time boundary)
    → Optional: random 64×64 spatial patch (for CPU memory)
    ↓
SST_ConvLSTM
    → ConvLSTMCell(1→32) → ConvLSTMCell(32→64) → 1×1 Conv2d
    → Autoregressive decoder: each pred feeds back as next input
    → Output: (B, horizon=7, 1, H, W)
    ↓
PhyLoss                              + MSELoss
    → Finite-difference kernels      → Pixel-wise prediction error
    → Advection-Diffusion residual   → Shapes the forecast distribution
    ↓
Wang et al. 2021 EMA Balancing
    → λ_phy = EMA(max|∇data| / mean|∇phy|)
    → Prevents gradient pathology
    ↓
Checkpoints + CSV logs
    ↓
DHW derivation (post-hoc)
    → Per-pixel monthly climatology from training split
    → Rolling 84-day hotspot accumulation
    → Bleaching alert level agreement vs. NOAA CRW ground truth
```

## Key Design Decisions

### Why Zarr (not NetCDF)?
Zarr stores data in chunks optimised for *time-series* reads. Because training iterates through time sequentially, `chunks=(30, -1, -1)` means each training batch touches at most 1–2 chunks. NetCDF's default chunking is optimised for spatial reads (all time for one location), which would be dramatically slower here.

### Why no interpolation extrapolation?

The source grids are not identical at their edges. The resolver interpolates
only inside the source support and preserves out-of-support values as missing.
Extrapolating at the boundary would create apparently valid ocean temperatures
or currents that were never observed. Small transient gaps may still be filled
by the validation policy; large gaps fail fast.

### Why `patch_size`?
The GBR canvas at 0.05° resolution is ~280×240 pixels. Full-resolution training on CPU requires loading the entire spatial domain for each batch (≈268 MB per batch at float32). `patch_size=64` reduces this to 4 MB per batch, making CPU-only training feasible.

### Why Z-score normalise from training split only?
Using validation or test statistics to normalise training data constitutes data leakage. The model would implicitly have access to statistics of the future (2023 test year), invalidating the evaluation. All normalisation parameters (mean, std) are computed only from the 2017–2022 training period.

### Why Wang et al. 2021 gradient balancing?
Physics losses and data losses operate at different scales and curvatures. Without balancing, the physics loss routinely dominates (larger gradient magnitudes), effectively turning the data loss off. Wang et al. 2021 dynamically rescales λ_phy each batch so neither term starves — this is critical for stable PINN training.

### Why the 2023 validation year?
NOAA confirmed 2023–2024 as a record-breaking global bleaching event (84.4% of reef area impacted). Using this as the held-out test year makes the evaluation an OOD (Out-of-Distribution) stress test: we specifically ask whether the model can generalise to thermal conditions beyond its training distribution. This is the hardest meaningful test.

| `training` | `batch_size` | 4 | Samples per gradient update |

## Extending This Work

**Add GPU support:**
```python
device = "cuda" if torch.cuda.is_available() else "cpu"
model  = model.to(device)
x_sst  = x_sst.to(device)
```
No code changes needed — the model and loss functions are device-agnostic.

**Add a new data variable (e.g. chlorophyll):**
1. Add an ERDDAP source to `config.yaml` under `data_sources`.
2. Add the variable to `DataIngestionFSM._merge_datasets()` in `data_pipeline.py`.
3. Add the channel to `ReefDataset.__getitem__()` in `dataset.py`.
4. Increase `in_channels` in `SST_ConvLSTM`.

**Extend the physics loss (e.g. add sea-surface heat flux):**
Add a new term to `PhyLoss.forward()` in `physics.py`. The Wang et al. balancing will automatically adapt the weights.

**Train on a different reef (e.g. Florida Keys):**
Change `lat_min/max` and `lon_min/max` in `config.yaml`. No code changes needed.
